# US-2 — уведомления о рейсе

Пользователь сначала находит рейс на нужную дату через существующий `GET /api/v1/flights/{flightIata}?date=...`. На сохранённый незавершённый рейс можно подписаться с сегодняшней даты UTC до 365 дней вперёд.

| Метод | URL | Тело JSON | Ответ |
|---|---|---|---|
| POST | `/api/v1/subscriptions/email` | `flightIata`, `flightDate`, `email` | `202`, `status=PENDING` |
| POST | `/api/v1/subscriptions/email/confirm` | `token` | `200`, `status=ACTIVE` |
| POST | `/api/v1/subscriptions/email/unsubscribe` | `token` | `200`, `status=UNSUBSCRIBED` |

Ответ содержит `message` и `status`. Повторный запрос подписки возвращает тот же нейтральный ответ. Неверный формат, недействительный токен, неизвестный либо завершённый рейс дают HTTP 400. После отписки можно подписаться заново, повторная отписка той же ссылкой идемпотентна.

```json
{"flightIata":"ZZ2000","flightDate":"2026-11-10","email":"demo@example.com"}
```

Запрос подписки сохраняет `PENDING` и задание отправки в одной транзакции. Отправщик создаёт две независимые 256-битные секретные ссылки непосредственно перед SMTP-отправкой. В PostgreSQL сохраняются только их SHA-256. Подтверждение одноразовое и доступно до 24 часов с момента запроса. Постоянная ссылка отписки остаётся у получателя в первом письме. GET открывает страницу с кнопкой, состояние меняется по POST. До подтверждения адреса уведомления об изменениях рейса не отправляются.

Повторное письмо можно запросить через 60 секунд. Лимит на адрес — пять запрошенных писем подтверждения за час для всех рейсов в сумме. При новом запросе для ожидающей подписки старые ссылки теряют силу. Выдача заданий сериализуется для одного адреса средствами PostgreSQL.

При свежем подтверждённом изменении статуса, задержки или ожидаемого прибытия `FlightService` сохраняет историю и ставит в очередь по одному письму на активную подписку в той же транзакции. Ключ события связан с `flight_status_logs.id`. Повтор того же состояния, fallback и устаревший ответ не создают писем. Планировщик Боба проверяет только уникальные выполнения с активными подписками и сохраняет ограничения периода и числа запросов к поставщику.

Отправщик выбирает готовую запись через `FOR UPDATE SKIP LOCKED`, проверяет состояние подписки и фиксирует результат каждой отправки отдельно. За один цикл обрабатывается до 20 записей. При ошибке SMTP письмо остаётся в очереди с повтором через 1, 2, 4 и 8 минут, после пятой неудачи получает `FAILED`. Сбой SMTP не влияет на готовность backend обслуживать рейсы и аналитику. При аварии между принятием письма SMTP и коммитом возможна повторная доставка. Для подтверждения используется последняя успешно зафиксированная ссылка.

## Локальная демонстрация

```powershell
docker compose -f docker-compose.yml -f docker-compose.mock.yml up -d --build
```

1. Найдите `ZZ2000` на сегодняшнюю дату через Swagger по адресу `http://localhost:8080/swagger-ui/index.html`.
2. Отправьте POST подписки на этот рейс и дату. Введите тестовый адрес.
3. Откройте тестовую почту Mailpit на `http://localhost:8025`. Нажмите ссылку и затем кнопку подтверждения.
4. При следующем изменении рейса появится отдельное письмо. Мок переводит ZZ2000 из `SCHEDULED` в `DELAYED`, затем в `LANDED` при реальных обращениях к поставщику. Redis кэширует состояние на три минуты.
5. Ссылка отписки находится в письме подтверждения.

Для обычного Compose почта также идёт в локальный Mailpit. Внешний SMTP настраивается через `.env` (`MAIL_HOST`, `MAIL_PORT`, `MAIL_FROM`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS`). `MAIL_PUBLIC_BASE_URL` должен указывать на доступный получателю backend. С настоящим AviationStack автоматический опрос по умолчанию выключен.
