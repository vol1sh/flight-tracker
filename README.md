## 📌 Этап 1. Формулировка проблемы и концепция

### Суть решаемой проблемы
Пассажиры и встречающие регулярно сталкиваются с внезапными переносами рейсов и сменой выходов на посадку, о которых табло аэропортов и авиакомпании сообщают с критическим опозданием. Отсутствие единого источника консолидированных данных и предиктивных оповещений приводит к опозданиям на пересадки, финансовым потерям и стрессу. Разрабатываемый сервис агрегирует статусы перелетов в реальном времени, отслеживает динамику задержек и заблаговременно информирует пользователей об изменениях расписания.

### Технологический стек
* **Серверная часть:** Java 21, Spring Boot 3.3, Spring Data JPA, Spring Validation
* **Отказоустойчивость:** Resilience4j (Circuit Breaker, Rate Limiter, Retry)
* **База данных и миграции:** PostgreSQL 16, Flyway Database Migrations
* **Кэширование:** Redis 7 (spring-boot-starter-data-redis)
* **Документация API:** Springdoc OpenAPI 3 (Swagger UI)
* **Клиентская часть:** React, TypeScript (SPA)
* **Контейнеризация и оркестрация:** Docker, Docker Compose

## 📋 Этап 2. Пользовательские сценарии и расчет нагрузок

### Пользовательские сценарии (User Stories)
* **US-1 (Пассажир):** Как авиапассажир, я хочу ввести номер рейса (например, `SU-100`) и дату, чтобы получить актуальный статус вылета, терминал, гейт и расчетное время задержки.
* **US-2 (Встречающий):** Как встречающий, я хочу подписаться на изменения статуса рейса, чтобы своевременно получить push- или webhook-уведомление о переносе времени посадки без постоянного обновления страницы.
* **US-3 (Аналитик / Администратор):** Как технический специалист, я хочу иметь доступ к историческим логам изменений задержек по конкретному борту или маршруту, чтобы оценивать надежность авиаперевозчика.
* **US-4 (Системный демон):** Как фоновый планировщик задач (Scheduler), я хочу опрашивать внешнее Aviation API с учетом лимитов (Rate Limiting) и размыканием цепи (Circuit Breaker), сохраняя снапшоты данных в Redis и PostgreSQL.

### Инженерный расчет нагрузок (Capacity Planning)

#### 1. Исходные параметры
* **Целевая аудитория (DAU):** $10\,000$ активных пользователей в сутки.
* **Средняя активность:** 1 пользователь совершает в среднем 8 запросов на чтение (просмотр табло, поиск рейса) и 0.5 запросов на запись (создание подписки на рейс).
* **Суточный объем запросов:**
  * Запросы на чтение (Read): $10\,000 \times 8 = 80\,000$ запросов/сутки.
  * Запросы на запись (Write): $10\,000 \times 0.5 = 5\,000$ запросов/сутки.
  * Фоновые синхронизации с внешним API: $1\,000$ отслеживаемых рейсов $\times 4$ обновления/час $\times 24 = 96\,000$ запросов/сутки.
  * Всего входящих HTTP-запросов к API: $85\,000$ запросов/сутки.

#### 2. Расчет RPS (Requests Per Second)
* **Средний RPS:**
  $$\text{RPS}_{\text{avg}} = \frac{85\,000}{86\,400} \approx 0.98 \approx 1.0\text{ req/s}$$
* **Пиковый RPS:**
  Учитывая, что 70% пользовательской активности приходится на дневные 8 часов с коэффициентом неравномерности $k = 3$:
  $$\text{RPS}_{\text{peak}} = \text{RPS}_{\text{avg}} \times 3 \approx 3.0 - 5.0\text{ req/s}$$
* **Соотношение Read / Write:** $\approx 16:1$ (система с преобладанием операций чтения).

#### 3. Расчет дисковой памяти под PostgreSQL (на 5 лет)
В системе персистентно хранятся две основные сущности:
1. **Таблица `flights`:**
   * Уникальных рейсов в сутки: $\approx 1\,000$ записей.
   * Размер одной строки (с учетом индексов и накладных расходов PostgreSQL): $\approx 400$ байт.
   * Объем за 5 лет:
     $$1\,000 \times 365 \times 5 \times 400\text{ байт} \approx 730\text{ МБ}$$

2. **Таблица `flight_status_logs` (аудит задержек):**
   * Количество изменений статуса на рейс: $\approx 6$ событий.
   * Записей в сутки: $1\,000 \times 6 = 6\,000$ записей/сутки.
   * Размер одной строки лога с индексами: $\approx 150$ байт.
   * Объем за 5 лет:
     $$6\,000 \times 365 \times 5 \times 150\text{ байт} \approx 1\,642\text{ МБ} \approx 1.64\text{ ГБ}$$

* **Суммарный объем базы данных за 5 лет:**
  $$\text{Storage}_{\text{5y}} = 0.73\text{ ГБ} + 1.64\text{ ГБ} \approx 2.37\text{ ГБ}$$
  С учетом 30% резерва на WAL-логи, служебные таблицы Flyway и vacuum overhead: **$\approx 3.2\text{ ГБ}$**. Для хранения пятилетней истории достаточно минимального SSD-накопителя.

#### 4. Расчет оперативной памяти под кэш (Redis)
* **Стратегия кэширования:** кэшируются метаданные только активных суточных рейсов ($1\,000$ рейсов).
* **Размер JSON-структуры рейса:** $\approx 2$ КБ.
* **TTL ключа:** 180 секунд (3 минуты).
* **Объем активного кэша данных:**
  $$1\,000 \times 2\text{ КБ} = 2\,000\text{ КБ} \approx 2\text{ МБ}$$
* **Накладные расходы Redis:** под структуры данных, ключи поиска по аэропортам и сессии выделяется **$64 - 128\text{ МБ}$ RAM**, что с запасом перекрывает пиковые всплески.

## 🏛 Этап 3. Архитектура системы (C4 Model)

### Уровень 1. Контекстная диаграмма (System Context)
```mermaid
C4Context
    title C4 Level 1: Контекстная диаграмма сервиса Flight Delay Tracker

    Person(passenger, "Пассажир / Встречающий", "Пользователь, отслеживающий статус рейса и задержки.")
    System(flightTracker, "Flight Delay Tracker Service", "Предоставляет API поиска рейсов, кэширует статусы и прогнозирует задержки.")
    System_Ext(aviationApi, "AviationStack / OpenSky API", "Внешний поставщик телеметрии и статусов перелетов в реальном времени.")

    Rel(passenger, flightTracker, "Просматривает расписание, подписывается на рейсы", "HTTPS / JSON")
    Rel(flightTracker, aviationApi, "Запрашивает статусы рейсов (Circuit Breaker)", "HTTPS / REST")

### Уровень 2. Диаграмма контейнеров (Containers)

```mermaid
C4Container
    title C4 Level 2: Диаграмма контейнеров сервиса мониторинга полетов

    Person(user, "Пользователь", "Пассажир или встречающий в браузере")

    Container(spa, "Single Page Application", "React, TypeScript", "Интерфейс поиска рейсов, просмотра табло задержек и оформления подписок")

    Container_Boundary(backend_boundary, "Серверный контур (Docker)") {
        Container(backend, "Backend Application", "Java 21, Spring Boot 3", "REST API, бизнес-логика расчетов, кэширование, Circuit Breaker Resilience4j")
        ContainerDb(postgres, "PostgreSQL 16", "Реляционная СУБД", "Хранение истории рейсов, расписаний и аудита задержек (миграции Flyway)")
        ContainerDb(redis, "Redis 7", "In-Memory Data Store", "Кэширование "горячих" рейсов (TTL 3 мин) и защита внешнего API от исчерпания лимитов")
    }

    System_Ext(aviationApi, "Aviation API", "AviationStack / OpenSky REST API")

    Rel(user, spa, "Просмотр табло, ввод номера рейса", "HTTPS")
    Rel(spa, backend, "Запросы данных о рейсах, создание подписок", "JSON / REST / :8080")
    Rel(backend, postgres, "Чтение/запись истории полетов", "JDBC (HikariCP) / :5432")
    Rel(backend, redis, "Чтение/запись кэшированных статусов", "Lettuce (RESP) / :6379")
    Rel(backend, aviationApi, "Синхронизация статусов с защитой через Circuit Breaker", "REST Client / HTTPS")
```
