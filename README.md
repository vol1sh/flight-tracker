## Этап 1. Формулировка проблемы и концепция

### Суть решаемой проблемы
Пассажиры и встречающие регулярно сталкиваются с внезапными переносами рейсов и сменой выходов на посадку, о которых табло аэропортов и авиакомпании сообщают с критическим опозданием. Отсутствие единого источника консолидированных данных и предиктивных оповещений приводит к опозданиям на пересадки, финансовым потерям и стрессу. Разрабатываемый сервис агрегирует статусы перелетов в реальном времени, отслеживает динамику задержек и заблаговременно информирует пользователей об изменениях расписания.

### Технологический стек
* **Бэкэнд:** Java
* **БД:** PostgresSQL
* **Фронтэнд:** JavaScript
* **Внешние апи:** Aviation Stack API

## Этап 2. Пользовательские сценарии и расчет нагрузок
### Пользовательские сценарии (User Stories)
1. **US-1 (Пассажир):** Как авиапассажир, я хочу ввести номер рейса (например, `SU-100`) и дату, чтобы получить актуальный статус вылета, терминал, гейт и расчетное время задержки.

**Критерии приемки:**
- пользователь может указать номер рейса и дату;
- при наличии данных, система отображает основные сведения о рейсе: статус, аэропорты вылета и прилёта, расчётное время и величину задержки;
- система показывает время последнего обновления данных;
- если актуальные данные временно недоступны, но в PostgreSQL сохранено последнее известное состояние рейса, система возвращает его с признаком dataFresh = false;
- если рейс не найден, пользователь получает соответствующий ответ.

2. **US-2 (Встречающий):** Как встречающий, я хочу подписаться на изменения статуса рейса, чтобы своевременно получить push- или webhook-уведомление о переносе времени посадки без постоянного обновления страницы.

**Критерии приемки:**
- пользователь получает текущий статус рейса и ожидаемое время прибытия;
- при наличии задержки система показывает её величину;
- при отмене рейса система явно отображает состояние CANCELLED;
- ответ содержит время последней успешной синхронизации с внешним источником.

3. **US-3 (Аналитик):** Как аналитик, я хочу просматривать историю задержек рейсов по выбранному маршруту или номеру рейса и получать показатели надежности, чтобы оценивать стабильность выполнения рейсов и выявлять маршруты с частыми задержками.

**Критерии приемки:**
- пользователь может выбрать рейс или маршрут для анализа;
- система отображает историю изменений статуса и задержек по сохранённым рейсам;
- система рассчитывает основные показатели надежности: среднюю задержку, долю рейсов без задержек и долю отменённых рейсов;
- система позволяет получить результат анализа на основе исторических данных, даже если внешний AviationStack API временно недоступен;
- если данных недостаточно для корректного анализа, система явно сообщает об этом пользователю;
- при использовании устаревших данных система отображает время последнего обновления.

### Расчет нагрузок (Capacity Planning)
#### 1. Исходные параметры
* **Целевая аудитория (DAU):** $10\,000$ активных пользователей в сутки.
* **Средняя активность:** 1 пользователь совершает в среднем 8 запросов на чтение (просмотр табло, поиск рейса) и 0.5 запросов на запись (создание подписки на рейс).
* **Суточный объем запросов:**
  * Запросы на чтение (Read): $10\,000 \times 8 = 80\,000$ запросов/сутки.
  * Запросы на запись (Write): $10\,000 \times 0.5 = 5\,000$ запросов/сутки.
  * Фоновые синхронизации с внешним API: $1\,000$ отслеживаемых рейсов $\times 4$ обновления/час $\times 24 = 96\,000$ запросов/сутки.
  * Всего входящих HTTP-запросов к API: $85\,000$ запросов/сутки.

#### 2. Расчет RPS (Requests Per Second)
* **Средний RPS:** $$\text{RPS}_{\text{avg}} = \frac{85\,000}{86\,400} \approx 0.98 \approx 1.0\ \text{req/s}$$
* **Пиковый RPS:** Учитывая, что 70% пользовательской активности приходится на дневные 8 часов с коэффициентом неравномерности \(k = 3\): 
$$ 
\text{RPS}_{\text{peak}} = \text{RPS}_{\text{avg}} \times 3 \approx 3.0 - 5.0\ \text{req/s} 
$$
* **Соотношение Read / Write:** \(\approx 16:1\) — система с преобладанием операций чтения.


#### 3. Расчет дисковой памяти под PostgreSQL (на 5 лет)
В системе персистентно хранятся две основные сущности:
1. **Таблица `flights`:**
   * Уникальных рейсов в сутки: $\approx 1\,000$ записей.
   * Размер одной строки (с учетом индексов и накладных расходов PostgreSQL): $\approx 400$ байт.
   * Объем за 5 лет:
     $$1\,000 \times 365 \times 5 \times 400\text{ байт} \approx 730\text{ МБ}$$

2. **Таблица `flight_status_logs` (аудит задержек):**
   * Количество изменений статуса на рейс: $\approx 6$ событий.
   * Записей в сутки: $1\,000 \times 6 = 6\,000$ записей/сутки.
   * Размер одной строки лога с индексами: $\approx 150$ байт.
   * Объем за 5 лет:
     $$6\,000 \times 365 \times 5 \times 150\text{ байт} \approx 1\,642\text{ МБ} \approx 1.64\text{ ГБ}$$

* **Суммарный объем базы данных за 5 лет:**
  $$\text{Storage}_{\text{5y}} = 0.73\text{ ГБ} + 1.64\text{ ГБ} \approx 2.37\text{ ГБ}$$
  С учетом 30% резерва на WAL-логи, служебные таблицы Flyway и vacuum overhead: **$\approx 3.2\text{ ГБ}$**. Для хранения пятилетней истории достаточно минимального SSD-накопителя.

#### 4. Расчет оперативной памяти под кэш (Redis)
* **Стратегия кэширования:** кэшируются метаданные только активных суточных рейсов ($1\,000$ рейсов).
* **Размер JSON-структуры рейса:** $\approx 2$ КБ.
* **TTL ключа:** 180 секунд (3 минуты).
* **Объем активного кэша данных:**
  $$1\,000 \times 2\text{ КБ} = 2\,000\text{ КБ} \approx 2\text{ МБ}$$
* **Накладные расходы Redis:** под структуры данных, ключи поиска по аэропортам и сессии выделяется **$64 - 128\text{ МБ}$ RAM**, что с запасом перекрывает пиковые всплески.

### 4.2. Реализованная система и границы MVP

При выполнении поиска фронтенд обращается к backend; backend проверяет номер и дату, находит запись в PostgreSQL и при необходимости запрашивает AviationStack. При невозможности получить данные приложение использует допустимый резервный сценарий или возвращает ошибку, не подставляя рейс за другую дату.

### 4.5. Качество кода и STDOUT-логирование
Для наблюдения за работой сервиса в `RequestLoggingFilter` используется фильтр `OncePerRequestFilter`, измеряющий время обработки через `System.nanoTime()` и логирующий:
- HTTP-метод и путь запроса;
- фактический HTTP-статус ответа;
- длительность обработки в миллисекундах (`durationMs`).

В `FlightService` также логируются нормализованный номер и дата поиска, источник (`source=DB`, `source=NONE` и другие сценарии), а также ситуации отказа внешнего поставщика. Логи выводятся в стандартный поток контейнера и доступны через Docker Compose.

### 4.7. Отладка и проверка работоспособности MVP
Для приёмки MVP используется матрица QA: `docs/qa/MVP_TEST_MATRIX.md`. Проверки подразделяются на автоматизированные (JUnit, MockMvc, Testcontainers, Vitest), HTTP/контейнерные и ручные (браузер, PostgreSQL, GitHub).

| Проверка | Инструмент | Что должно быть подтверждено |
|---|---|---|
| Сборка и работа сервисов | Docker Compose + `/actuator/health` | PostgreSQL, Redis, backend, frontend доступны |
| Поиск сохранённого рейса | Браузер + DevTools Network + SQL | Номер, дата и поля совпадают в JSON, UI и БД |
| Обязательная дата и ошибочный номер | `curl`, `FlightControllerContractTest` | Корректные HTTP 400 |
| Изоляция разных дат | `FlightServiceTest`, `FlightRepositoryIntegrationTest` | Номер за разные даты не смешивается |
| Отказ внешнего API и fallback | `FlightServiceTest` | Не подставляются данные другой даты; корректная деградация |
| История и реакции интерфейса | `App.test.tsx`, браузер | Карточка, история, ошибки, предупреждение об устаревших данных |
| Реальное обращение к AviationStack | Backend + безопасный лог поставщика | Подтверждён успешный ответ без утечки ключа |
| STDOUT | Docker Compose logs | Путь, статус, `durationMs`, источник |
| CI | GitHub Actions | Backend и frontend jobs зелёные на проверенном SHA |

**Команды для повторяемой проверки:**
```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
curl -i http://localhost:8080/actuator/health
curl -i http://localhost:3000/
docker compose logs --tail=100 backend
```

Для автоматических backend-тестов локально нужен Maven/Java 21 либо Maven-контейнер с доступом к Docker Engine для Testcontainers; для frontend — Node.js/npm либо соответствующая проверка CI. Самый воспроизводимый способ показать выполнение в отчёте — ссылка на конкретный workflow GitHub Actions.
